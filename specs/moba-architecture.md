# MOBA 精简架构文档

> **实现状态（2026-08-05）**：规划中。本次只交付架构文档，不新增 Rust 代码、不接入现有 A 股项目的运行链路。
>
> **偏差记录**：本文把第一版收缩为可验证的单机纵切片，并把规则层、渲染层、网络层拆开；相对 Gemini / GPT 原文的保留、修改与说法校正见 §10。

## 1. 项目目标

第一版只做出一个**本地可操作的 2D MOBA 纵切片**：一张地图、两个英雄、移动、普攻、一个技能、血量、死亡复活和两个简单 AI，玩家可以操作自己的英雄把 AI 打死。

开发方式是 **AI 协作驱动**：AI 负责把规则拆成小步、先写测试、实现代码并根据容器中的编译/测试输出迭代；用户在本地负责运行 Bevy 窗口、判断操作手感和确认画面。第一版的完成标准是“规则可测、窗口可玩”，不是完整商业 MOBA，也不是一次把未来全部系统搭完。

## 2. 与本仓库的关系

本文件存放在 `zz497676-ai/stock`，但它与仓库现有的 A 股资金监控 Python 项目**没有业务关系、没有代码依赖、没有运行时依赖**。当前只是借这个会话指定的仓库存放文档，方便评审路线。

MOBA 代码的落地位置尚未决定：可以新建独立仓库，也可以将来放到本仓库的 `game/` 子目录。无论采用哪一种，游戏应拥有独立的 Cargo workspace、依赖和构建入口；不得把 A 股采集器、网页流程、GitHub Actions 或 Python 运行逻辑混进游戏架构。本次唯一改动是新增本文件，暂不创建 `game/`、Cargo 文件或 Rust 源码。

## 3. 三条核心原则

### 3.1 规则层是一个纯 Rust crate

所有游戏规则放在 `moba_core`。它不依赖 Bevy、不画画、不联网、不读键盘，也不读取系统时间；它只接收规则层输入，推进一个 tick，并返回规则事件。规则更新的唯一入口固定为：

```rust
pub fn step(world: &mut World, inputs: &[Input]) -> Vec<Event>;
```

这里的 `World` 是 `moba_core` 自己定义的普通数据结构，不是 Bevy 的 ECS `World`；`Input` 和 `Event` 也是规则层的数据类型。输入来源可以是本地键盘、AI 或网络包，但核心不需要知道来源。入口每调用一次只推进一个固定 tick，不把任意的渲染帧时间或网络副作用带进规则。

### 3.2 第一版不用 ECS 写规则

第一版用普通 `struct`、`enum` 和 `Vec` 表达英雄、技能、血量、冷却、地图和事件。这样做的目的不是否定 ECS，而是把第一条可玩闭环的学习成本压到最低：规则可以在没有窗口的情况下测试，数据也能直接从测试断言中读懂。

Bevy 只做“开窗口、读输入、画出状态”的薄适配层。第一阶段不要求理解或设计 Bevy 的 Entity / Component / System；等对象数量、场景复杂度或性能确实需要时，再把渲染对象迁移到 ECS。

### 3.3 服务器权威 + 固定 tick，但推迟到第二阶段

服务器权威和固定 tick 仍是联网版本的目标：客户端提交输入，服务器在固定 tick 中调用规则层并决定移动、伤害、技能是否合法，客户端只展示服务器状态。第一阶段先在单进程内直接调用同一套 `moba_core`，用它验证规则；第二阶段再把调用方移动到服务器，先用进程内 channel，再换本机 socket。这样保留正确方向，但不让第一次写 Rust 就同时承担网络同步问题。

## 4. crate 划分与依赖方向

| crate | 一句话职责 | 何时加入 |
|---|---|---|
| `moba_core` | 纯规则模拟：`World`、`Input`、`Event`、英雄/技能/AI 和 `step`。只使用 Rust 标准库，不依赖任何其他项目 crate。 | 阶段 1 |
| `moba_client` | Bevy 客户端：窗口、键盘输入、占位图形、摄像机和状态展示；阶段 2 之后不拥有伤害结算权。 | 阶段 1 |
| `moba_server` | 权威服务器进程：接收输入，在固定 tick 调用 `moba_core`，广播快照/事件并处理断线。 | 阶段 2 |
| `moba_net` | 网络协议与传输适配：输入、快照、事件的线格式，以及阶段 3 的 renet 接入；不写游戏规则。 | 阶段 3（阶段 2 先可用简单 socket） |

依赖方向如下，箭头表示“依赖”：

```text
moba_client ────────> moba_core
     │
     └───────────────> moba_net ────────> moba_core

moba_server ────────> moba_core
     │
     └───────────────> moba_net

moba_core ───────────> Rust 标准库
```

`moba_core` 不反向依赖 `moba_client`、`moba_server` 或 `moba_net`，也不依赖 Bevy、renet 或 socket。这个单向边界是可测试性的来源：容器可以只编译和测试规则，不需要图形设备、网络服务或窗口。

阶段 1 的实际工作区只有 `moba_core` + `moba_client`；此时 `moba_client` 在本地进程直接调用 `moba_core::step`。服务器和网络 crate 不因为“未来可能需要”而提前创建。

## 5. 第一版内容边界

### In：第一版必须有

- 一张小型俯视角 2D 地图，先用简单几何形状表达地面和边界。
- 两个可区分的英雄，至少有位置、移动速度、生命值和存活状态。
- 键盘控制移动。
- 普攻：有目标/范围、伤害和攻击冷却。
- 一个主动技能：有释放条件、范围或目标、伤害/效果和冷却。
- 血量、死亡、复活，以及可从画面或事件中看见的状态变化。
- 两个简单、可重复的 AI 行为，例如接近目标、攻击目标和在死亡后重新参与战斗；不使用机器学习。
- 最小可读反馈：英雄位置、血条、攻击/技能结果和死亡/复活状态。占位图形即可。

### Out：明确不进入第一版

- 小兵、兵线和刷兵系统。
- 防御塔、基地和完整胜负条件。
- 装备、商店、经济、等级和复杂成长系统。
- 3D 模型、骨骼动画、粒子特效和高质量美术。
- 匹配、房间服务、账号、登录、持久化和社交系统。
- 为第一版提前引入 NavMesh、回滚预测、定点数、Nakama、Axum 大厅或 P2P/WebRTC。

“能操作英雄打死 AI”是第一版的纵切片验收线；任何不服务于这条验收线的系统都先记到后续列表，不在阶段 1 偷渡进来。

## 6. 四阶段路线图

### 阶段 1：单机、不联网

先建立独立 Cargo workspace 中的 `moba_core` 和 `moba_client`。在 `moba_core` 中用普通结构实现世界初始化、移动、普攻、技能冷却、伤害、死亡/复活和两个 AI；每个规则先有测试，再由 `moba_client` 把输入转成 `Input`、调用 `step`，用占位图形展示结果。

完成判据：

- `cargo test -p moba_core` 退出码为 0，规则测试全绿，至少覆盖移动、攻击范围/冷却、技能冷却、伤害、死亡复活和 AI 行为。
- 用户在本地启动客户端后可以操作自己的英雄移动、普攻或放技能，并在画面中把 AI 打死；AI 的血量归零、死亡状态和复活过程可观察。
- 该阶段没有网络进程、socket 或 renet，规则测试不需要打开 Bevy 窗口。

### 阶段 2：拆出服务器

把 `moba_core::step` 的调用权从客户端移到 `moba_server`。先在同一进程中用 channel 传递 `Input` 和服务器快照/事件，确认权威边界后，再把 channel 换成本机 socket；两次替换都不改规则层入口。

完成判据：

- 客户端不再调用 `step`，也不再自行修改或结算伤害；它只能发送输入并展示服务器返回的生命值、位置和事件。
- 集成测试或可追踪日志能证明：一次攻击造成的血量变化只在服务器世界发生，客户端伪造“已造成伤害”的消息不会被服务器采纳。
- 关闭客户端后服务器仍能继续运行并维护世界；用进程内 channel 和本机 socket 各跑通一次，客户端观察到的结果一致。

### 阶段 3：接入 renet 2.0

把 `moba_net` 接入 renet 2.0，明确输入、快照、事件和连接状态的协议。服务器固定 tick 读取各客户端输入，调用 `moba_core::step`，再向客户端发送可展示的结果；客户端不把网络消息当成规则裁判。

完成判据：

- 启动一个服务器和两个客户端，两个客户端能互相看见对方英雄的位置和存活状态。
- 客户端只提交技能意图，技能是否在冷却、是否在范围内、是否命中和造成多少伤害均由服务器判定；两个客户端看到的结果一致。
- 任一客户端断线后，服务器能识别连接失效并清理、冻结或标记该玩家，其他客户端仍可继续运行；断线不会让服务器崩溃或把角色永久卡在半次技能结算中。

### 阶段 4：预测与 3D

在阶段 3 的权威协议稳定后，才增加客户端移动预测、服务器校正和 3D 表现层。预测只优化操作反馈，不改变服务器对伤害和技能的裁决；3D 也只是客户端表现替换，不能反过来污染 `moba_core`。

完成判据：

- 在可重复的网络模拟中加入 100 ms 延迟，玩家移动仍可操作，不会因为等待服务器回包而完全卡住。
- 延迟恢复后客户端状态能收敛到服务器状态，不能因预测重复造成伤害、重复触发技能或生成幽灵英雄。
- 同一套阶段 1 规则在 3D 客户端中仍能完成移动、攻击、技能、死亡和复活；若 3D 只改善画面而没有通过延迟验收，不算阶段 4 完成。

## 7. 技术选型与版本

以下版本是本次通过 crates.io sparse index 实测到的结果，文档只记录已核实的版本：

| 项目 | 版本/环境 | 用途与结论 |
|---|---|---|
| Rust | 1.94.1（容器可用） | 规则 crate 和客户端开发环境；`cargo new`、`cargo add serde`、`cargo check` 已跑通。 |
| Bevy | 0.19.0 | 已确定的客户端渲染与输入引擎；阶段 1 只使用薄适配层。 |
| renet | 2.0.0 | 阶段 3 的网络传输/连接层；不提前进入阶段 1。 |
| macroquad | 0.4.16 | 已实测但不选用；本方案已确定 Bevy 0.19.0，避免同时维护两套渲染路线。 |

容器当前只安装了 `x86_64-unknown-linux-gnu` target，这足以验证无图形依赖的规则层，但不代表已经验证了其他平台构建。阶段 1 的画面验证仍须在用户本地完成。

现在明确不做的技术：

- **定点数**：第一版规则量小，先用普通数值把玩法闭环跑通；定点数会增加类型、运算和调试成本。定点数也不会自动保证跨平台一致，真正的确定性还依赖运算顺序、随机源、tick 和序列化协议。
- **全局回滚预测**：第一版没有多人对战和高延迟需求，先做服务器权威与必要的阶段 4 移动预测，不提前承担回滚状态、输入重放和调试成本。
- **NavMesh**：两个简单 AI 用直接移动/简单状态机即可，地图和单位数量尚未证明需要导航网格。
- **Matchbox**：它偏向 WebRTC/P2P 路线，与本方案的专用服务器权威路线不一致。
- **Nakama**：账号、匹配、持久化等后端能力都在第一版范围外，现在引入会扩大部署和学习面。
- **Axum 大厅**：没有房间/登录/大厅需求，先不为不存在的产品流程搭服务。
- **照搬 Veloren**：Veloren 是大型开放世界 RPG，不能当作本项目的 MOBA 架构模板；参考它只会把内容和系统规模带偏。

## 8. AI 协作约定

容器没有显示图形界面的能力，Bevy 窗口无法在这里验证。因此把可自动验证和必须人工验证的边界写死：

| 验证对象 | 谁负责 | 具体方式 |
|---|---|---|
| `moba_core` 的规则逻辑、边界条件和单元测试 | AI 可在容器内完成，用户看测试结果 | 运行 `cargo test -p moba_core`；不需要图形设备，通常是秒级反馈。 |
| Bevy 是否能开窗、键盘输入是否生效、画面是否正确 | 用户必须在本地完成 | 启动 `moba_client`，实际操作英雄，检查窗口、血条、技能反馈、死亡/复活和卡顿。 |
| 手感、移动速度、攻击距离、技能是否“好用” | 用户本地判断，AI 根据描述调整规则参数 | 不能用容器里的编译成功替代主观体验验收。 |
| 多进程、两客户端和断线表现 | AI 可写协议/集成测试，用户本地复现窗口体验 | 先看服务端日志与测试，再由用户观察两个客户端。 |

每个 feature 的交付顺序固定为：**先写测试 → 再写规则 → 最后接渲染**。如果是网络 feature，则在规则测试后增加协议/集成测试，再接客户端表现；不能先用画面“看起来动了”来证明伤害、技能或胜负规则正确。

Bevy 的首次编译耗时较长，是 AI 迭代循环里最大的摩擦点之一：每次为了改一个血量规则都触发图形依赖，会显著降低反馈速度。把规则放进不依赖 Bevy 的 `moba_core`，既是架构边界，也是减少现实开发摩擦的办法。

## 9. 你现在需要学的 / 现在不用学的

### 现在需要学

- Rust 的最小必需集：`struct`、`enum`、方法、模块、`Vec`、所有权/借用，尤其是 `&mut World` 为什么允许规则原地更新。
- Cargo 的最小工作流：`cargo new`、workspace、`Cargo.toml`、`cargo check`、`cargo test`、`cargo run`，以及如何看编译器指出的文件/行号。
- **`cargo test` 怎么读**：先看命令退出码；区分“编译失败”和“测试运行失败”；找到失败测试名、`assert` 的期望值/实际值和第一处 panic；修复后重新运行单个测试，再跑完整包测试。测试全绿是规则完成判据的一部分。
- 游戏规则的基本词汇：输入、tick、状态、事件、生命值、冷却、范围、碰撞边界和简单状态机。
- 最小 Bevy 使用面：能照着适配层模板开窗口、读取键盘、画简单 2D 形状、更新显示。不要求先理解 Entity / Component / System 的设计思想。
- Git 的最小使用面：看 diff、提交小步变更、在本地保留可回退的阶段性结果。

### 现在不用学

- Bevy 的 Entity / Component / System 体系、查询、Schedule、Plugin 设计和复杂 ECS 优化；它们不是第一阶段规则实现的前置知识。
- 网络协议、连接管理、服务器部署、快照压缩、预测/校正和断线重连；这些到阶段 2/3 再按实际接口学习。
- 定点数、全局回滚、NavMesh、匹配/账号/大厅后端和商业级数据库；它们当前没有对应的验收需求。
- 3D 摄像机、光照、模型、骨骼、粒子和资产流水线；阶段 1 的占位 2D 图形足够验证玩法。

后续如果进入阶段 2，再学习 ECS 和网络不是“推翻前面重写”，而是为客户端表现和进程边界增加适配层；`moba_core` 的规则入口和测试仍然是稳定锚点。

## 10. 与 Gemini / GPT 两份原文档的偏差记录

### 保留的判断

1. 保留服务器权威：多人版本必须由服务器决定伤害、技能是否合法和最终状态。
2. 保留固定 tick：把规则推进从渲染帧率中分离出来，方便服务器模拟和网络同步；只是把实现推迟到阶段 2。
3. 保留 Bevy 作为渲染引擎，并采用已实测的 Bevy 0.19.0；保留 renet 作为阶段 3 的网络候选，并采用已实测的 renet 2.0.0。
4. 保留“先做小范围可玩版本”的方向，但把“最小”进一步写成了 in/out 清单和逐阶段验收判据。

### 做出的实质改动

1. 把规则从引擎中抽成纯 Rust `moba_core`，对外固定 `step(&mut World, &[Input]) -> Vec<Event>`；规则不依赖 Bevy、网络或渲染对象。
2. 删除第一版用 ECS 写规则的前置要求，第一阶段用普通 `struct` + `Vec`，只让 Bevy 负责输入和画面。
3. 把完整四 crate 架构改成分阶段落地：阶段 1 只有 `moba_core` + `moba_client`，阶段 2 才有 `moba_server`，阶段 3 才有 `moba_net` + renet。
4. 把“联网 MOBA”拆成单机规则、进程内权威、socket、renet、预测/3D 五个可观察的演进节点，避免第一行代码就陷入多人同步。
5. 增加 AI 协作约定：规则测试由容器快速验证，窗口/手感/画面由用户本地验证，并固定“测试 → 规则 → 渲染”的交付顺序。

### 过头说法的校正

| 原文档中的倾向性说法 | 本文采用的准确表述 |
|---|---|
| “AI 能自动修复 90% 以上编译错误” | 不承诺任何百分比。AI 可以读取 `cargo check` / `cargo test` 输出并尝试修复，但测试结果、用户本地窗口和真实手感仍是验收依据。 |
| “定点数自动保证跨平台一致” | 定点数最多是减少浮点差异的一种工具，不能自动保证一致；还要控制随机性、运算顺序、tick、协议和平台实现。第一版因此不引入它。 |
| “一开始就完整采用 ECS / 网络架构更稳” | 对第一版没有这个必要；先让纯规则和单机纵切片可测，再在需求出现时增加 ECS 和服务器边界。 |
| “把大型开源项目的架构直接照搬即可” | Veloren 等大型开放世界 RPG 的问题规模不同，不能作为 MOBA 第一版模板；这里只吸收可验证的边界思想，不照搬系统。 |

这份偏差记录不是否定原文档的长期方向，而是把“未来可能需要”与“今天必须完成”分开，让一个没有 Rust 经验的人知道第一步和停在哪里。

## 11. 边界与风险

- **Bevy 版本风险**：Bevy 仍在快速迭代，文档、示例和 API 可能不完整，版本间也可能有破坏性变更。实现时固定 Bevy 0.19.0，升级必须单独评估，不能把网上的其他版本示例直接当作事实。
- **容器验证边界**：容器没有显示图形界面，AI 不能在这里证明窗口能开、画面好看或操作顺手；本地运行是必需的验证环节，不是可选的最后演示。
- **网络风险后移但不会消失**：输入顺序、快照频率、断线、延迟、预测校正和状态收敛的难点会在阶段 3 才真正暴露。阶段 1 的单机通过不等于联网已经可行。
- **确定性风险**：第一版不使用定点数和全局回滚，不宣称跨平台位级一致；若之后需要竞技级重放或回滚，要先用测试证明现有数值模型不够，再单独设计。
- **内容/美术风险**：单人开发 MOBA 的美术、动画、音效、地图和英雄内容量很大。第一版只用占位图形验证玩法，不能把“规则跑通”误报为“产品完成”。
- **范围风险**：小兵、防御塔、装备、匹配和账号都很容易把纵切片拖回完整架构。新增需求必须先写进某个阶段的完成判据，否则留在 out 清单中。
- **生产边界**：本方案没有覆盖反作弊、账号安全、持久化、运维、负载测试和商业化服务；即便阶段 4 完成，也只能说明原型路线被验证，不能直接视为生产系统设计。
